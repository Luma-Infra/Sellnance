## 3. 업비트 429 Client Error (Too Many Requests) 원인 분석 및 완벽 방어
터미널에 발생하던 `🚨 통합 프록시 에러 (upbit - KRW-META2): 429 Client Error`의 근본 원인을 분석하고 4중 방어벽을 구축했습니다.

### 🔍 원인 분석
1. **IP 쿼터 경합**: 새로고침 시 `/api/market-data`가 업비트 전 종목(287개) Ticker를 8개 청크로 딜레이 없이 0.1초 만에 연타 호출하면서, 동시에 들어온 차트 캔들 요청과 겹쳐 업비트의 **공용 IP 초당 10회(1초 롤링 윈도우)** 한도 초과.
2. **기존 쿨다운 결함**: 기존 캔들 프록시의 429 재시도 딜레이가 겨우 `0.25초`여서 1초 롤링 윈도우가 리셋되기 전에 2차 시도를 들이받아 무조건 에러 발생.
3. **파라미터 초과**: 프론트에서 `limit=500` 요청 시 업비트 공식 규격(최대 200개) 초과.

### 🛡️ 적용된 해결책
* **`modules/candle_proxy.py`**:
  * 429 감지 시 즉시 전역 쿨다운(`trigger_cooldown(1.5)`) 발동하여 후속 요청을 안전 대기열로 격리.
  * 점진적 백오프(1.0s, 2.0s) 적용 3회 재시도 엔진 구축.
  * 429 발생 시 무서운 예외 트레이스백 대신 안전한 빈 배열(`[]`)을 반환하여 차트 UI 렌더링 보호.
* **`modules/exchange_api.py`**:
  * Ticker 청크 크기를 40개 ➡️ 70개로 확대(총 요청수 8회 ➡️ 4회 축소).
  * 청크 간 `80ms` 안전 페이싱 딜레이를 부여해 캔들 요청용 **IP 쿼터 상시 마진 확보**.
* **`modules/adapter.py`**: 업비트 캔들 `count`를 `min(limit, 200)`으로 자동 보정.
* **`static/quickview.js`**: 퀵뷰 8개 카드 로딩 시 카드별 `50ms` 순차 시차(Stagger) 적용.

## 4. 타임프레임별 적응형 캐시 수명(TTL) 차등화 엔진 구축
고정 30초 캐시를 폐지하고 타임프레임의 특성에 맞춘 동적 캐시 TTL 엔진(`get_candle_ttl`)을 도입했습니다.

| 타임프레임 구분 | 캐시 유지 시간 (TTL) | 비고 |
| :--- | :---: | :--- |
| **과거 히스토리 (to 파라미터)** | **10분 (600초)** | 이미 확정된 과거 봉이므로 영구 불변 |
| **일봉 / 주봉 / 월봉 (1d, 1w, 1M)** | **5분 (300초)** | 5분 동안 외부 호출 차단, 0ms 즉각 반환 |
| **시간봉 (1h, 4h, 12h)** | **3분 (180초)** | 시간 단위 완성 봉 |
| **중기 분봉 (15m, 30m)** | **1분 (60초)** | 1분 동안 외부 호출 차단 |
| **단기 분봉 (3m, 5m)** | **30초** | 30초 동안 외부 호출 차단 |
| **초단기 분봉 (1m)** | **15초** | 15초 동안 외부 호출 차단 |

> **💡 핵심 무결성 보장:**  
> 최신 봉의 실시간 가격/등락률은 프론트엔드 웹소켓이 매초 갱신하므로, 과거 캔들 배열을 5~10분 캐싱해도 차트의 실시간성에는 전혀 영향을 주지 않습니다.

## 5. Cloudflare Worker 아웃바운드 엣지 프록시 인프라 구축 & 백엔드 연동
동시 접속자 급증 시 단일 서버 IP 한계를 극복하기 위해 글로벌 엣지 프록시 파이프라인을 구축했습니다.

* **Cloudflare Worker 배포**:
  * URL: `https://upbit-proxy.7883121.workers.dev/`
  * 역할: 들어오는 타겟 URL을 Cloudflare의 전 세계 수백 개 분산 엣지 IP 풀로 업비트에 중계.
* **백엔드 연동**:
  * `.env`: `CF_WORKER_PROXY_URL` 환경변수 등록.
  * `modules/candle_proxy.py` & `modules/exchange_api.py`:
    * 업비트 캔들 및 Ticker 시세 요청을 Cloudflare Worker를 통해 호출.
    * Cloudflare Worker 장애 시 **기존 직통 URL로 1회 자동 안전 폴백(Fallback)** 구현.
* **효과**: 우리 백엔드 서버의 고유 IP가 업비트에 직접 노출되지 않으며, IP 차단 위험 0% 달성.

## 6. Railway 인프라 (1 vCPU / 1 GB) 동시 500명 수용 능력 진단
* **웹소켓 부하 0%**: 실시간 시세는 유저 브라우저 ↔ 거래소 간 직통 웹소켓 연결로 서버 부하 전무.
* **정적 파일 95% 흡수**: Cloudflare 프록시 CDN이 JS/CSS/폰트 캐싱 처리.
* **API 처리 여유**: `/api/market-data` 등은 메모리 반환(< 2ms)으로 초당 1,000+ RPS 처리 가능 (500명 동시 접속 시 CPU 5~15%, RAM ~300MB 수준으로 충분히 감당).
* **Railway 주의사항**: 로컬 `.env`에 추가한 `CF_WORKER_PROXY_URL`을 Railway 대시보드의 **Variables** 탭에도 등록 필요.
